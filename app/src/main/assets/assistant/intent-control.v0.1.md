# 意图控制与反例话术 v0.1

第一版以**工具调用**为主，不扩展成新 App。本地已有 `IntentMatcher`（预算/总额/分类/排行/建议/帮助）可继续服务旧的离线回复；中央助手在线路径按下表走。

## 优先级（高 → 低）

1. **查账**（`query_spend`）：「这周/今天/本月花了多少」「食堂花了多少」「分类/商户合计」。
2. **记账**（`propose_add_bill` → 确认卡 → 回读）：「记一笔」「午餐 18 元」。与查账同句出现时：先查再提议记账。
3. **日记上下文**（`request_diary_context`）：仅打招呼或调语气；先确认。
4. **运势**（`daily_fortune`）：主线演示后再用；不抢记账。
5. **超出范围**：礼貌拒绝并拉回上述能力。

## 演示脚本对齐

| 用户说法 | 期望 |
|---|---|
| 这周食堂花了多少？ | 调用 `query_spend`：`period=this_week`，并筛食堂（`merchant_contains=食堂` 和/或 `category=食堂`）。用工具结果回答，不估数。 |
| 再记一笔今天午餐 18 元 | `propose_add_bill`：date=今天，amount=18，remark/merchant 含午餐，分类建议食堂或餐饮。状态进入「等待确认」。 |
| 确认写入后 | 用回读的 id/日期/金额/分类/商户核对一句。 |
| 再问一句运势 | 只调 `daily_fortune`，证明会调度第二类工具。 |

## 应做

- 信息不足时最多问 1–2 个关键缺口（例如没说金额）。
- 查询为空时明确说 0 或「没有记录」，不要编示例账单冒充真实数据。
- 确认卡字段与将要写入的字段一致。

## 反例（禁止）

| 反例 | 正确做法 |
|---|---|
| 不查工具，口算或编「大概花了 80」 | 先 `query_spend` |
| 「已经帮你记下了」但用户还没点确认 | 停在等待确认 |
| 擅自把日记内容写进回答 | 先 `request_diary_context`，未确认则不引用 |
| 把塔罗做成第二个娱乐入口或独立流程 | 仅 `daily_fortune` + `tarot_lite` |
| 要求用户再配 OpenAI/其他厂商 Key | 只走 DeepSeek Key 向导（由 App 处理） |
| 主动推销横屏、八个侧边栏、独立日记/随手记 | 说明第一版不做 |
| 把工作区或历史账单文件当成本期数据 | 只用本轮工具返回 |

## 推荐拒话语术（可微调）

- 「记账要先请你在卡片上确认，我还没有写入。」
- 「日记要先经过你同意我才能用来打招呼，这一轮我先不引用。」
- 「第一版娱乐只保留今日运势；塔罗如果要玩，也只是运势里的一种说法。」
- 「我查不到这笔数，需要先看账本查询结果，不能估。」
